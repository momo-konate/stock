1. VUE D'ENSEMBLE DE L'APPLICATION
═══════════════════════════════════════════════════════════════════════════════

StockPro est une application complète de gestion de stock pour les petites et 
moyennes entreprises. Elle permet de :

✅ Gérer l'inventaire des produits (ajout, modification, suppression)
✅ Enregistrer les ventes et générer des reçus
✅ Suivre les dépenses et la caisse
✅ Gérer les clients et leurs dettes
✅ Gérer les fournisseurs
✅ Créer plusieurs utilisateurs (admin et vendeurs)
✅ Générer des rapports et statistiques
✅ Exporter les données en Excel

2. ARCHITECTURE GÉNÉRALE
═══════════════════════════════════════════════════════════════════════════════

L'application suit une architecture CLIENT-SERVEUR séparée :

┌─────────────────────────────────────────────────────────────────────────────┐
│                                                                             │
│  FRONTEND (React + Vite)          ←→         BACKEND (Node.js + Express)   │
│  Port: 5173                       HTTP/JSON  Port: 5000                     │
│                                                                             │
│  - Interface utilisateur          ←→         - API REST                    │
│  - Gestion de l'état                         - Logique métier              │
│  - Validation côté client                    - Validation côté serveur     │
│  - Affichage des données                     - Accès base de données       │
│                                                                             │
│                                              ↓                              │
│                                                                             │
│                                         BASE DE DONNÉES                     │
│                                         (SQLite)                            │
│                                         - Stockage persistant               │
│                                         - Relations entre tables            │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘

POURQUOI CETTE SÉPARATION ?
─────────────────────────────
✅ Séparation des responsabilités (frontend = affichage, backend = logique)
✅ Évolutivité : on peut changer le frontend sans toucher au backend
✅ Sécurité : la logique sensible reste côté serveur
✅ Réutilisabilité : l'API peut servir à d'autres clients (mobile, etc.)

3. TECHNOLOGIES UTILISÉES ET POURQUOI
═══════════════════════════════════════════════════════════════════════════════

BACKEND (Serveur)
─────────────────────────────
🔹 Node.js + Express
   POURQUOI ? 
   - JavaScript partout (même langage frontend/backend)
   - Rapide et performant pour les API
   - Grande communauté et beaucoup de packages
   - Facile à déployer

🔹 SQLite (via Sequelize ORM)
   POURQUOI ?
   - Pas besoin d'installer un serveur de base de données
   - Fichier unique facile à sauvegarder
   - Parfait pour les petites/moyennes applications
   - Sequelize permet de changer facilement vers MySQL/PostgreSQL plus tard

🔹 JWT (JSON Web Tokens)
   POURQUOI ?
   - Authentification sans session (stateless)
   - Sécurisé et standard de l'industrie
   - Permet de vérifier l'identité sans toucher la DB à chaque requête

🔹 Joi (Validation)
   POURQUOI ?
   - Validation robuste des données entrantes
   - Empêche les données invalides d'entrer dans la DB
   - Messages d'erreur clairs et personnalisables

🔹 Helmet + Rate Limiting
   POURQUOI ?
   - Protection contre les attaques courantes
   - Limite les tentatives de connexion (anti-brute force)
   - Sécurise les headers HTTP

FRONTEND (Interface)
─────────────────────────────
🔹 React 19
   POURQUOI ?
   - Composants réutilisables
   - Virtual DOM = performance
   - Écosystème riche
   - Facile à maintenir

🔹 Vite
   POURQUOI ?
   - Démarrage ultra-rapide (HMR instantané)
   - Build optimisé
   - Meilleur que Create React App

🔹 TailwindCSS
   POURQUOI ?
   - Design rapide avec classes utilitaires
   - Cohérence visuelle
   - Responsive facile
   - Pas de CSS à écrire

🔹 Axios
   POURQUOI ?
   - Meilleur que fetch() natif
   - Intercepteurs pour ajouter le token automatiquement
   - Gestion d'erreurs simplifiée

🔹 React Router
   POURQUOI ?
   - Navigation entre pages (login, dashboard, etc.)
   - Protection des routes (redirection si non connecté)

🔹 Recharts
   POURQUOI ?
   - Graphiques beaux et responsives
   - Facile à utiliser avec React

🔹 XLSX
   POURQUOI ?
   - Export Excel professionnel
   - Compatible avec tous les tableurs

ARCHITECTURE EN COUCHES (LAYERED ARCHITECTURE)
───────────────────────────────────────────────

Routes → Middleware → Controllers → Models → Database

1. ROUTES : Définissent les URLs (ex: /api/products)
2. MIDDLEWARE : Vérifient le token, valident les données
3. CONTROLLERS : Logique métier (que faire ?)
4. MODELS : Interaction avec la base de données
5. DATABASE : Stockage persistant

POURQUOI CETTE STRUCTURE ?
───────────────────────────
✅ Séparation des responsabilités (chaque fichier a un rôle précis)
✅ Facile à tester (on peut tester chaque couche séparément)
✅ Facile à maintenir (on sait où chercher en cas de bug)
✅ Scalable (on peut ajouter des fonctionnalités facilement)

6. FLUX DE DONNÉES ET COMMUNICATION
═══════════════════════════════════════════════════════════════════════════════

EXEMPLE : CRÉATION D'UN PRODUIT
────────────────────────────────

1. L'utilisateur remplit le formulaire ProductForm.jsx
2. Il clique sur "Créer"
3. Le composant appelle handleProductSubmit() du hook useProducts.js
4. Le hook appelle productService.create(data) dans api.js
5. api.js envoie une requête POST http://localhost:5000/api/products
6. Le backend reçoit la requête dans product.routes.js
7. Le middleware validate() vérifie les données avec Joi
8. Le middleware protect() vérifie le token JWT
9. Le controller createProduct() est appelé
10. Le model Product.create() insère dans la DB
11. Le backend renvoie le produit créé en JSON
12. Le frontend reçoit la réponse
13. Le hook met à jour l'état local
14. React re-rend automatiquement la liste des produits

SCHÉMA DU FLUX :
────────────────

User Input → Component → Hook → Service → API Request
                                              ↓
                                         Backend Route
                                              ↓
                                         Middleware
                                              ↓
                                         Controller
                                              ↓
                                         Model (DB)
                                              ↓
                                         Response ←─┐
                                              ↓     │
Service ← Hook ← Component ← React Re-render ←─────┘

7. SÉCURITÉ ET AUTHENTIFICATION
═══════════════════════════════════════════════════════════════════════════════

SYSTÈME D'AUTHENTIFICATION JWT
───────────────────────────────

1. L'utilisateur se connecte (email + password)
2. Le backend vérifie les credentials
3. Si OK, génère un JWT token contenant l'ID de l'utilisateur
4. Le frontend stocke le token dans localStorage
5. À chaque requête, le token est envoyé dans le header Authorization
6. Le backend vérifie le token et identifie l'utilisateur

MIDDLEWARE DE PROTECTION
─────────────────────────

protect() : Vérifie que l'utilisateur est connecté
admin() : Vérifie que l'utilisateur est admin

ISOLATION DES DONNÉES
──────────────────────

Chaque utilisateur ne voit que SES données :
- Un admin voit tout ce qu'il a créé + ce que ses vendeurs ont créé
- Un vendeur voit uniquement ce qu'il a créé lui-même
- Système de parentId : les vendeurs sont liés à leur admin créateur

VALIDATION EN DOUBLE
─────────────────────

1. Frontend : validation immédiate (UX)
2. Backend : validation stricte avec Joi (sécurité)

PROTECTION CONTRE LES ATTAQUES
───────────────────────────────

✅ Helmet : Sécurise les headers HTTP
✅ Rate Limiting : Limite les tentatives de connexion
✅ CORS : Contrôle les origines autorisées
✅ Bcrypt : Hash des mots de passe (jamais en clair)
✅ Joi : Validation stricte des entrées (anti-injection)

POURQUOI SEQUELIZE (ORM) ?
──────────────────────────

Au lieu d'écrire du SQL brut :
  SELECT * FROM products WHERE userId = 1

On écrit :
  Product.findAll({ where: { userId: 1 } })

AVANTAGES :
✅ Plus lisible et maintenable
✅ Protection contre les injections SQL
✅ Facile de changer de DB (SQLite → MySQL)
✅ Gestion automatique des relations

9. POURQUOI CETTE ARCHITECTURE ?
═══════════════════════════════════════════════════════════════════════════════

PRINCIPES DE CONCEPTION APPLIQUÉS
──────────────────────────────────

1. SÉPARATION DES RESPONSABILITÉS (Separation of Concerns)
   ✅ Frontend = Affichage
   ✅ Backend = Logique + Données
   ✅ Chaque fichier a un rôle précis

2. DRY (Don't Repeat Yourself)
   ✅ Hooks réutilisables (useProducts, useSales)
   ✅ Composants réutilisables (Modal, ProductForm)
   ✅ Services centralisés (api.js)

3. SINGLE RESPONSIBILITY PRINCIPLE
   ✅ Un controller = une ressource (products, sales, etc.)
   ✅ Un hook = une fonctionnalité
   ✅ Un composant = une vue

4. SCALABILITÉ
   ✅ Facile d'ajouter de nouvelles fonctionnalités
   ✅ Facile de passer à une vraie DB (PostgreSQL)
   ✅ Facile d'ajouter une app mobile (même API)

5. MAINTENABILITÉ
   ✅ Code organisé et structuré
   ✅ Facile de trouver où est un bug
   ✅ Facile d'onboarder un nouveau développeur

6. SÉCURITÉ
   ✅ Validation en double (frontend + backend)
   ✅ Authentification robuste (JWT)
   ✅ Isolation des données par utilisateur
   ✅ Protection contre les attaques courantes

ALTERNATIVES CONSIDÉRÉES ET REJETÉES
─────────────────────────────────────

❌ Monolithe (tout dans un seul projet)
   → Moins flexible, difficile à maintenir

❌ MongoDB au lieu de SQL
   → Pas de relations strictes, moins adapté pour la gestion de stock

❌ Redux au lieu de Hooks + Context
   → Trop complexe pour cette taille d'app

❌ Next.js au lieu de Vite
   → Overkill, on n'a pas besoin de SSR

❌ TypeScript
   → Ajouterait de la complexité sans bénéfice majeur ici
